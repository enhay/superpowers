## Implementation

- Understand the real path before choosing a solution. Prefer existing repo helpers, standard-library/native-platform features, and installed dependencies before adding code or dependencies. Do not reuse compatibility helpers already marked for removal. Minimize new files and abstractions without sacrificing edge-case correctness.
- Repair incorrect schemas and semantics at their source; migrations remain subject to authorization. Compatibility during a migration needs an explicit removal condition. Do not build permanent normalization or fallback chains over a wrong model.
- A lock, a retry, a fallback, a null guard, or a catch-all requires both a business scenario and a technical condition, both stated: who hits it under what circumstances, AND that it genuinely occurs at this system's actual scale, traffic, and deployment shape. Example: in a 2B back office, "two operators edit the same order at once" holds as a scenario, but a few dozen users' concurrency means it will not happen — no lock. The same scenario on a 2C payment callback does hold. Pointing at code and saying "theoretically possible here" satisfies neither condition; "a caller might", "under high load", "for robustness", and "we might change this later" are not trigger conditions either. This does not waive trust-boundary validation or security.
- Match the file's existing style. Comments explain why, not the editing history. Mark temporary code or a known ceiling as `TODO(owner): <trigger condition>`.
- Python: prefer `uv`. JSON/YAML: prefer `jq`, `yq`, or `gron`, unless the project already has a toolchain.

## Verification and evidence

- Define the observable result before editing and verify it afterward. Use the lightest evidence that covers the changed behavior: typecheck/build for compilation, unit tests for algorithms, APIs for business rules/contracts/permissions, and database plus logs for persisted state.
- A new test needs a current requirement plus a named later change that would silently break it; a code change, an existing test, or the rule's category (invariant, data semantics, permission, contract) alone does not qualify. Reuse existing checks first. Add at most one per rule the change introduces or alters, on the case most likely to regress, and verify the other branches by throwaway means. Synthetic cases fit the boundary's input contract and a real failure mode; never restate tunable constants. Strict red-green only when the user or a project rule requires it; otherwise a bug fix reproduces the failure when feasible, and a refactor passes the same checks before and after.
- When logic is removed, delete the tests that served only it; prove the cleanup with one-time searches, typechecks, or builds, never with permanent tests derived from deleted branches, keywords, or workarounds. Never invert assertions, swap expected values, or add "removed code is absent" checks to pass the suite. Keep tests for requirements still valid, adapting only setup when only the implementation changed; change an expectation only when the requirement changed. A failure alone never justifies deleting or weakening a test; retire a defense's coverage only after confirming its risk is gone.
- A test assertion anchors only to: a pure function or selector return value; a persisted or API field; an explicit `data-state`/`data-phase`/aria attribute; an error, permission, or result code. Never text, CSS classes, DOM hierarchy, snapshots, element counts, or mere existence — no "close enough", and plan text or existing tests grant no exemption. If none fits, write no unit test; run a smoke check and say so.
- Use a browser or screenshots only when the user explicitly asks; a reference image, a plan line, or a project doc is not such a request. When asked, run the relevant non-browser checks first; otherwise leave visual acceptance to the user and say so in one line.
- Frequency, coverage, absence, and claims such as "never happened" or "always fails" require real data with a stated scope and event deduplication. A directly reproduced compile/runtime failure can establish a deterministic defect. Distinguish missing data from failed processing. After a backfill, re-check each item through its real API/frontend consumption path.
- Stop once the accepted result is observed; widen the checks only for a new change, a new failure, or evidenced doubt, and verify with throwaway means — verifying does not by itself justify a new test, script, or sample set in the repo. Report baseline failures accurately.
